    Docker deployment

    Four containers — MySQL, the Laravel API, the Next.js storefront, and Caddy, which terminates TLS and renews the certificates — started with one command on any machine that runs Docker. No PHP, Node, Composer, or database server has to be installed on the host, and no separate proxy or certbot job is needed for HTTPS.

    Nine sections. Read the first four to get a working site on your own domain with a valid certificate; the rest covers data, backups, upgrades, and the production checklist.

    When to use this instead of a manual install

    The manual path in Installation is still the right choice when you already have a web server, or when your host does not allow Docker. Use the containers when you want a clean, repeatable runtime:

    • You are moving to a fresh Linux server and do not want to install PHP extensions, nginx, and Node by hand.
    • You develop on Windows or macOS and want the same environment a Linux server will have.
    • You want to try the platform, or take a copy of a live site, without touching your existing stack.
    What the host needs
    Requirement Details
    Docker Engine 24+ On Windows or macOS that means Docker Desktop with the WSL 2 or Hyper-V backend running. Compose v2 is included.
    Memory 4 GB free for the first build (the Next.js build is the heavy step). Around 1 GB at runtime.
    Ports 80 and 443 on the host, answered by Caddy for both hostnames. The storefront and the API listen on loopback ports (3000 and 8080) that exist for debugging on the server only.
    Domain One domain you control, with two names pointed at the server: example.com for the storefront and api.example.com for the API and admin panel. Certificates are issued for both automatically.
    Disk Image layers plus a named volume for the database, uploads, and lesson videos.
    Docker is not required

    The download runs without it. If you are unsure whether your host supports containers, use the manual installation and keep this chapter for later — the two paths share the same code and the same database schema.

    Quick start

    From the folder that contains docker-compose.yml (the download root):

    1. Point the domain at the server

      At your DNS provider, create two A records with the server's public IPv4 address. Both names must resolve before the first start, otherwise Caddy has nothing to request a certificate for:

      Type Name Value Serves
      A@ (or www)203.0.113.10The storefront at https://example.com.
      Aapi203.0.113.10The API and the admin panel at https://api.example.com.

      Confirm with dig +short example.com and dig +short api.example.com: both must print the server's address.

    2. Create the environment file

      cp .env.docker.example .env

      Open it and set the two domains, plus the administrator account and the database passwords. The next sections explain every key.

    3. Start the stack

      docker compose up -d

      The first run builds both images (5–10 minutes, mostly the storefront), migrates and seeds the database, and then Caddy requests the two certificates. --build is only needed after the code or a domain changes.

    4. Open the site

      docker compose ps
docker compose logs --tail=40 api caddy

      Every service should show running, and the Caddy log ends with a line saying the certificate was obtained. If the storefront answers but the home page is empty, the API container is not healthy — its logs will say why.

    Where things are
    URL What
    https://example.comThe storefront: catalog, course pages, checkout, dashboards.
    https://api.example.com/adminThe Filament admin panel.
    https://example.com/api/v1/settingsDataA public API endpoint — use it as a health check for the backend.
    https://api.example.com/storage/…Uploaded thumbnails, avatars, and the logo.
    127.0.0.1:3000, 127.0.0.1:8080The raw containers, reachable from the server itself only — useful with curl when a page misbehaves.

    What runs where

    Four services, one private network, four named volumes (database, storage, and two for Caddy's certificates and account).

    Service Built from Runs Published
    mysql mysql:8.4.11 (pinned patch release) MySQL server for the application database, utf8mb4. Data lives on the lms-mysql volume; only the API container can reach it. not published
    api localhost/Dockerfile nginx + php-fpm + a queue worker under supervisord, PHP 8.4 with pdo_mysql, GD, intl, and zip. Serves the API, /admin, and /storage, and delivers queued mail and notifications. port 80 → 127.0.0.1:8080
    web frontend/Dockerfile Node 22 running the Next.js standalone server (node server.js). port 3000 → 127.0.0.1:3000
    caddy caddy:2-alpine Terminates TLS for both domains, redirects http:// to https://, serves the storefront, and forwards /api, /sanctum and the login/register posts on the storefront host — plus everything on the API host — to the api container. Its rules live in docker/caddy/Caddyfile. 80, 443

    Why the storefront needs two API addresses

    Server-rendered pages fetch the API from inside the web container, while the browser fetches it from the visitor's device. In a container, localhost means the container itself, so the two callers cannot share one address:

    Variable Used by Value in the stack
    NEXT_PUBLIC_API_PROD_URL The browser: login, cart, checkout, dashboards. https://WEB_DOMAIN — the storefront's own origin. Caddy forwards /api and /sanctum to Laravel, so the session and XSRF-TOKEN cookies stay first-party.
    API_INTERNAL_URL Server Components: the home page, course pages, legal pages. http://api — the service name on the compose network

    The second hostname, API_DOMAIN, is not used by the storefront's JavaScript at all: it is the address of the admin panel, the uploaded files (APP_URL), the Google sign-in callbacks, and the payment webhooks.

    Public values are baked in at build time

    Anything starting with NEXT_PUBLIC_ is compiled into the browser bundle. Changing a domain or a published port therefore needs a rebuild, not just a restart: docker compose up -d --build web.

    Domain, HTTPS and certificates

    Caddy is the only container exposed to the internet. It answers on ports 80 and 443 for both hostnames, redirects plain HTTP to HTTPS, and obtains a Let's Encrypt certificate for each name the first time that name resolves at the server. Nothing has to be generated, copied, or renewed by hand, and no cron job has to be installed: a certificate lives 90 days and Caddy renews it about 30 days before it expires.

    What is automated and what is not
    Task Handled by
    First certificate for both namesCaddy, as soon as DNS resolves and ports 80/443 reach it — once, at the first start.
    Renewal every 90 daysCaddy, in the background. It also retries a failed order on its own.
    HTTP → HTTPS redirectCaddy.
    Keeping the certificate across updates and rebootsThe lms-caddy-data volume, which holds the certificates and the ACME account key.
    Pointing the DNS records at the serverYou, at the registrar. This is the only manual step.

    Watching and managing the certificate

    The log is the place to look. A successful order is a line containing certificate obtained successfully:

    # what happened during issuance and renewal
docker compose logs caddy | grep -i certificate

# the files on the volume, one folder per hostname
docker compose exec caddy ls /data/caddy/certificates/acme-v02.api.letsencrypt.org-directory
    • Expiry notices by mail. Add email you@example.com as the first line inside the global block of docker/caddy/Caddyfile, then docker compose restart caddy. Without it the certificate still works and still renews; you just do not get Let's Encrypt's warning mail.
    • Start over with a certificate. Only needed if a name was moved to a different server while the old one kept serving it. Delete only Caddy's data, never the storage volume: docker compose down, docker volume rm lms_lms-caddy-data, docker compose up -d. Let's Encrypt allows five certificates per name per week, so repeated resets hit a rate limit.
    • Moving to another domain. Put the new names in WEB_DOMAIN and API_DOMAIN, keep the old DNS records until the new ones answer, then docker compose up -d --build. Caddy finds two new names and issues their certificates; the old ones stay in the volume and expire unused.
    • Behind an existing proxy. If the server already runs nginx, Apache or Traefik, stop Caddy with docker compose stop caddy (and remove it from docker-compose.yml so a restart does not bring it back). The app containers stay on 127.0.0.1:3000 and 127.0.0.1:8080 for your own proxy; keep X-Forwarded-For and X-Forwarded-Proto intact.
    HSTS is on

    Both hostnames send Strict-Transport-Security for a year, so browsers refuse to open them over plain HTTP again. That is what you want on a live site; if you ever move the installation back to a server without TLS, remove those two header lines from the Caddyfile first.

    Environment reference

    All of these live in the .env file next to docker-compose.yml. Docker Compose reads it automatically.

    Key Default Notes
    WEB_DOMAINexample.comThe storefront host — the address visitors type. Its certificate, the API origin, CORS and Sanctum settings all follow from it. The web image has to be rebuilt after a change.
    API_DOMAINapi.example.comThe API and admin-panel host: /admin, /storage, Google callbacks and payment webhooks. Gets its own certificate.
    API_PORT8080Loopback debugging port for the backend. Not reachable from outside the server.
    WEB_PORT3000Loopback debugging port for the storefront.
    ADMIN_EMAILnone — requiredThe first administrator, created on the first boot only. Must be an address you can receive mail at, since password resets go there. The stack refuses to start while it is empty.
    ADMIN_PASSWORDnone — requiredYour own password for /admin. Nothing is generated and no account is shipped, so an empty value stops the boot with an explanation instead of leaving a panel nobody can sign in to. Used only while the database is still empty; to change it later, set a new value and re-run the seeder.
    APP_KEYemptyLeave empty: the first boot generates one and stores it on the volume. Set it only to reuse an existing key.
    MAIL_MAILERlogEmails go to storage/logs/laravel.log until you configure SMTP in the admin panel or add MAIL_* variables here.
    NEXT_PUBLIC_MEDIA_HOSTSemptyExtra image hosts (a bucket or CDN) for next/image.
    Values the stack derives for you

    APP_URL, FRONTEND_URL, SANCTUM_STATEFUL_DOMAINS, CORS_ALLOWED_ORIGINS and both NEXT_PUBLIC_* build arguments are computed from the two domains inside docker-compose.yml, so they cannot fall out of step with each other. Change the domains, not those derived keys.

    Payments and Google sign-in

    Gateway keys and the Google client are edited in the admin panel at /admin, so they do not belong in this file. Stripe webhooks need a public HTTPS address, which means going through the production checklist below before taking payments.

    What the first boot does

    The API container's entrypoint prepares the installation, then starts nginx and php-fpm:

    1. Generates an application key

      Unless APP_KEY is set, a key is generated and written to storage/app/.app-key on the volume, so later restarts reuse it and encrypted sessions stay valid.

    2. Waits for the database and prepares storage

      The entrypoint polls MySQL until it accepts connections, so a slow first start-up of the database cannot abort the API boot. It then links public/storage to the public disk and fixes ownership so both nginx and php-fpm can read uploads.

    3. Migrates every boot, seeds once

      php artisan migrate --force runs on every start, so an updated image also updates the schema of an existing installation. Seeding runs only the first time: a marker file storage/app/.installed records it, so restarts never duplicate the starting content or overwrite the admin account.

      The administrator is part of that first seeding: it is created from ADMIN_EMAIL and ADMIN_PASSWORD without any manual command, and the boot log confirms it with Administrator created: .... A fresh server therefore needs docker compose up -d and nothing else.

    After signing in at /admin with the exact ADMIN_EMAIL and ADMIN_PASSWORD from .env, remove the demo courses you do not want. The panel's dashboard shows the rest of the first-run checklist.

    Changing the administrator later

    The seeding step only runs once, so editing .env afterwards changes nothing by itself. To move the account to another address, or to recover a forgotten password, set the new values in .env, recreate the API container so it receives them, and run the seeder again — it updates that account instead of creating a second one:

    docker compose up -d api
docker compose exec api php artisan db:seed --class=AdminSeeder --force

    Use a new ADMIN_EMAIL to add a second administrator; the existing account is left untouched.

    Day-to-day operations

    Logs and a shell

    docker compose logs -f api web caddy
docker compose exec api php artisan about
docker compose exec api sh

    Where the data lives

    The database lives in the lms-mysql volume (inside the MySQL container), the uploaded files in the lms-storage volume mounted at /var/www/html/storage:

    • lms-mysql — the whole database.
    • app/public/ — thumbnails, avatars, logos, certificates.
    • app/private/ — lesson videos and attachments, streamed through Laravel.
    • logs/ — application log.

    TLS certificates and the Let's Encrypt account key live in the lms-caddy-data volume, and Caddy's own state in lms-caddy-config. Neither needs backing up: if the volume is lost, the certificates are requested again on the next start.

    Queue and failed jobs

    The api container runs php artisan queue:work under supervisord, so queued mail and notifications are delivered without any extra service. It restarts by itself and is recycled every hour. To check it from the server:

    # the worker is a supervised process next to nginx and php-fpm
docker compose exec api ps -ef | grep queue:work

# what it is doing (mail bodies appear here while MAIL_MAILER=log)
docker compose logs -f api | grep -i queue

    A job that fails three times moves to failed_jobs. List them, read the exception, and retry after fixing the cause (usually SMTP credentials):

    docker compose exec api php artisan queue:failed
docker compose exec api php artisan queue:retry all
docker compose exec api php artisan queue:flush   # discard them instead

    Backup and restore

    # Backup (writes a tarball into the current folder)
docker run --rm -v lms_lms-storage:/data -v "$PWD":/backup alpine \
  tar czf /backup/lms-storage.tgz -C /data .

# Restore into an empty stack
docker compose down
docker run --rm -v lms_lms-storage:/data -v "$PWD":/backup alpine \
  sh -c "rm -rf /data/* && tar xzf /backup/lms-storage.tgz -C /data"
docker compose up -d

    Stopping the stack with docker compose stop or down keeps the volume. docker compose down -v deletes it — the next start is a fresh install.

    Updating the code

    docker compose up -d --build

    Migrations run on every start, so a new image updates the schema of an existing installation by itself. The volumes are untouched: the database, uploads, videos and the generated APP_KEY survive a rebuild. To see what is pending, or to apply it without restarting the container:

    docker compose exec api php artisan migrate --force

    Going live

    The stack already serves HTTPS on your domain; the certificates section above covers that side. What is left is the part only you can do: real secrets, real mail, a restricted firewall, and a backup that leaves the machine.

    The end-to-end walkthrough — server preparation, DNS checks, the verification list, backups and updates — is in Deploy to a server. The steps below are the short version.

    1. Use the real domain and a real mailer

      WEB_DOMAIN=example.com
API_DOMAIN=api.example.com

MAIL_MAILER=smtp
MAIL_HOST=smtp.yourprovider.com
MAIL_PORT=587
MAIL_SCHEME=smtp
MAIL_USERNAME=postmaster@example.com
MAIL_PASSWORD=your-smtp-password
MAIL_FROM_ADDRESS=no-reply@example.com
      docker compose up -d --build

      With log as the mailer no verification link and no password reset ever leaves the server. Rebuilding is required because the storefront origin is compiled into the bundle.

    2. Harden the account and the exposure

      Move the administrator to a real mailbox and a long password with the seeder command above (the values in .env only apply when the seeder runs), keep APP_DEBUG off (the image already sets it), and leave only ports 22, 80 and 443 open in the firewall — the API and storefront ports are bound to 127.0.0.1 and are not reachable from outside.

    3. Schedule the backups

      Run the dump and tarball commands from the previous section nightly and copy them off the server. Certificates need no backup: Caddy reissues them on a fresh volume.

    The database runs next to the app

    MySQL uses a modest amount of memory but handles the concurrent writes of an active course site: sessions, cache, queued jobs and the course data all use the same server. Back it up by dumping the schema, separately from the storage volume:

    docker compose exec mysql sh -c 'exec mysqldump -u root -p"$MYSQL_ROOT_PASSWORD" --single-transaction --databases "$MYSQL_DATABASE"' > lms-db.sql

    To restore it into a fresh stack, start the services and pipe the dump back in: docker compose exec -T mysql sh -c 'exec mysql -u root -p"$MYSQL_ROOT_PASSWORD"' < lms-db.sql.

    Images are served unoptimised

    Inside a container the Next.js image optimiser cannot reach the host's published ports, so the Docker image serves original uploads and lets the browser load them from the API origin. Pages are slightly heavier than a manual install behind one domain. Resize large thumbnails before uploading if that matters to you.

    Troubleshooting

    Symptom Cause and fix
    Storefront loads, home page is empty or shows an error The server could not reach the API. Check docker compose logs api and that API_INTERNAL_URL is still http://api.
    Login fails with 419, or the cart empties itself The address in the browser does not match WEB_DOMAIN (for example www. versus the bare name), so the session cookie belongs to the other host. Put the exact name visitors use in WEB_DOMAIN, then docker compose up -d --build.
    Images and the logo are broken API_DOMAIN is wrong, or the stack was restarted instead of rebuilt after the change. docker compose up -d --build web.
    The site answers on https:// but the browser warns about the certificate Either the certificate has not been issued yet (DNS missing, port 80 blocked, another server already listening on 80/443 — docker compose logs caddy says which), or you are on a placeholder name such as localhost where Caddy uses its own local authority.
    502 or "connection refused" from the backend Caddy is up but the container behind it is not. docker compose logs api shows the PHP error; usually a storage permission problem or a syntax error in a config file.
    required variable ADMIN_PASSWORD is missing a value There is no .env, or one of the two administrator values is empty. .env.docker.example is only a template — compose reads .env and nothing else, so copy it first and fill in ADMIN_EMAIL and ADMIN_PASSWORD. The same message appears when the stack was started from a fresh download without that step.
    dependency failed to start: container lms-mysql-1 is unhealthy docker compose logs mysql repeating exec format error means the MySQL image itself is broken, not the data: the floating 8.4 tag published on 3 November 2026 contains a zero-byte docker-entrypoint.sh. The stack pins mysql:8.4.11 for exactly that reason. If you bump the tag, check it first with docker run --rm --entrypoint sh mysql:8.4.x -c 'ls -l /usr/local/bin/docker-entrypoint.sh' — the file must not be 0 bytes. Any other MySQL crash (bad password in .env, corrupted volume) is shown in the same log.
    $'\r': not found when the container starts The entrypoint was checked out with Windows line endings. The image strips them at build time, so rebuild; if you edited the script, save it with LF.
    Port already allocated Another web server on the host (Apache, nginx, a panel) already uses port 80 or 443. Stop it — Caddy has to own both. A collision on WEB_PORT or API_PORT only affects debugging: change the value in .env.
    Emails never arrive Two causes. MAIL_MAILER=log writes messages to the log instead of sending them, so configure SMTP first. Otherwise the queued job has not run: check that the worker is up with docker compose logs api | grep -i queue and look for failures in failed_jobs (docker compose exec api php artisan queue:failed). An empty MAIL_FROM_ADDRESS is fine — the sender falls back to no-reply@ plus the API host — but a broken SMTP host or password still ends up there.
    Videos will not play after moving the site Private videos are streamed with signed URLs built from APP_URL, which follows API_DOMAIN; make sure that value is the address visitors reach, then restart the API container.
