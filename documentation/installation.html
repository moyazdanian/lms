    Installation on a server

    The supported deployment is Docker Compose on a Linux server: four containers — MySQL, the Laravel API with the admin panel, the Next.js storefront, and Caddy for HTTPS — started with one command. No PHP, Node, Composer, MySQL, nginx, or certificate tool is installed on the host.

    Ten sections, in the order you need them. The .env and SMTP sections are the two to read carefully; everything else is copy-and-paste.

    What you need

    One Linux server, one domain you control, and nothing else. The stack in this chapter is the only installation path this manual documents.

    Minimum for a real course site
    Item Details
    Server Ubuntu 22.04 or 24.04 LTS (any Linux with Docker works). 2 vCPU and 2 GB RAM minimum; 4 GB makes the first build comfortable. Root or a sudo-capable SSH user.
    Disk 40 GB minimum. Lesson videos are the real cost — if they will be large, use an S3-compatible bucket instead (Admin → Settings → Storage).
    Domain One domain with the ability to add A records. Two hostnames are used: the storefront and the API.
    Ports 80 and 443 open on the server, answered by the Caddy container. The application containers stay on loopback ports behind it.
    Docker Docker Engine 24+ with the Compose v2 plugin. The install commands below set both up.

    What runs where

    Service Built from Runs Published
    mysql mysql:8.4.11 (pinned patch release) The application database, utf8mb4. Data lives on the lms-mysql volume. not published
    api localhost/Dockerfile nginx + php-fpm + a supervised queue worker, PHP 8.4 with pdo_mysql, GD, intl, and zip. Serves the API, /admin, and /storage, and delivers queued mail and notifications. 127.0.0.1:8080
    web frontend/Dockerfile Node 22 running the Next.js standalone server. 127.0.0.1:3000
    caddy caddy:2-alpine Terminates TLS for both domains, redirects HTTP to HTTPS, serves the storefront, and forwards /api, /sanctum, the login/register posts and /auth/* callbacks on the storefront host to the API container. 80, 443
    Why two hostnames

    The storefront is a Node server and the API (with the admin panel) is nginx + PHP. They also use overlapping paths — the admin panel loads its assets from /css and /js, which would collide with the storefront on one hostname. Two hostnames, one certificate each, no path juggling:

    • example.com → the storefront
    • api.example.com → the API, /admin, /storage, webhooks

    The browser talks to the storefront origin for /api and /sanctum, which keeps Sanctum's session and CSRF cookies first-party. Uploaded files, the admin panel, and payment webhooks go straight to the API host. Server-side rendering inside the Docker network uses the private service name, so no request loops back through the proxy.

    Point the domain at the server

    At your DNS provider, create these records with the server's public IPv4 address (add AAAA records if you have IPv6):

    Type Name Value Purpose
    A@203.0.113.10The storefront at https://example.com. Use www instead if that is the address visitors should type — pick one.
    Aapi203.0.113.10The API and admin panel at https://api.example.com.

    Verify before touching the server — certificate issuance fails while DNS is still propagating:

    dig +short example.com
dig +short api.example.com

    Both commands must print the server's IP. Propagation is usually minutes, occasionally a few hours.

    Install Docker and open two ports

    1. Install Docker Engine and Compose

      sudo apt update && sudo apt upgrade -y
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker "$USER"

      Log out and back in so the group applies, then check that both commands answer:

      docker version
docker compose version

    2. Open only the ports you need

      sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
      Nothing else may own port 80 or 443

      Caddy inside the stack publishes those two ports, and Docker writes its own firewall rules for them, so ufw deny 8080 does not hide a published port. The API and storefront ports are already bound to 127.0.0.1 and are never public. If Apache, nginx, or a hosting panel already listens on 80/443, stop it first — sudo ss -ltnp | grep -E ':80|:443' shows which process owns them.

    Put the project on the server

    Upload the download (scp, rsync, or the host's file manager) into /opt/lms. The folder that contains docker-compose.yml is the one you work from for every command in this chapter.

    sudo mkdir -p /opt/lms
sudo chown "$USER":"$USER" /opt/lms
# upload the download into /opt/lms, then:
cd /opt/lms
ls docker-compose.yml .env.docker.example localhost frontend

    The three things that must be there: docker-compose.yml, the localhost/ folder (Laravel), and the frontend/ folder (Next.js). Images are built from those folders on the server.

    The .env file

    Docker Compose reads .env from the folder that holds docker-compose.yml — not the Laravel .env you may have seen in other PHP projects. This is the only application configuration file you edit; the Caddyfile is touched only if you want certificate-expiry email.

    cd /opt/lms
cp .env.docker.example .env
nano .env

    Minimum to fill in before the first start

    APP_NAME=My Academy

WEB_DOMAIN=example.com
API_DOMAIN=api.example.com

ADMIN_EMAIL=owner@example.com
ADMIN_PASSWORD=a-long-unique-password

DB_DATABASE=lms
DB_USERNAME=lms
DB_PASSWORD=a-long-random-database-password
DB_ROOT_PASSWORD=another-long-random-password

MAIL_MAILER=smtp
MAIL_HOST=smtp.yourprovider.com
MAIL_PORT=587
MAIL_SCHEME=smtp
MAIL_USERNAME=postmaster@example.com
MAIL_PASSWORD=your-smtp-password
MAIL_FROM_ADDRESS=no-reply@example.com
MAIL_FROM_NAME="My Academy"

    Every key

    Key Required What it does
    APP_NAME no Fallback application name used by the API and mail templates. The name visitors see in the storefront, page titles, and certificates comes from Admin → General Settings.
    WEB_DOMAIN yes The storefront host — the address visitors type. Its certificate, the browser's API origin, CORS and Sanctum settings all follow from it. The web image must be rebuilt after a change.
    API_DOMAIN yes The API and admin-panel host: /admin, /storage, Google callbacks, and payment webhooks. Gets its own certificate.
    API_PORT no Loopback debugging port for the backend, default 8080. Not reachable from outside the server.
    WEB_PORT no Loopback debugging port for the storefront, default 3000.
    ADMIN_EMAIL yes The first administrator, created on the first boot only. Must be an address you can receive mail at, since password resets go there. The stack refuses to start while it is empty.
    ADMIN_PASSWORD yes Your password for /admin. Nothing is generated and no account is shipped, so an empty value stops the boot with an explanation. Used only while the database is still empty.
    DB_DATABASE, DB_USERNAME, DB_PASSWORD, DB_ROOT_PASSWORD yes in practice Used when MySQL initialises its volume. Change them before the first start; changing them later needs matching changes inside the database.
    APP_KEY no Leave empty: the first boot generates one and stores it on the storage volume. Set it only to reuse an existing key.
    MAIL_* yes for real mail SMTP transport and sender. MAIL_MAILER=log writes messages to the container log instead. See Email (SMTP).
    NEXT_PUBLIC_MEDIA_HOSTS no Comma-separated extra hosts for images that come from a bucket or CDN, for example my-bucket.s3.eu-west-1.amazonaws.com. Leave empty when the backend serves uploads.
    Keys that are set for you

    APP_ENV, APP_DEBUG, DB_HOST, DB_PORT, TRUSTED_PROXIES, FILESYSTEM_DISK, LESSON_VIDEO_DISK, and VIDEO_SERVING_MODE are written by docker-compose.yml, not read from this file. Video storage and delivery are changed in Admin → Settings → Storage. Payment, Google, and S3 credentials also live in the panel; see Admin panel → Settings.

    Do not copy localhost/.env.example or frontend/.env.example into the stack. The containers receive their values from Compose, and the API image deliberately removes any Laravel .env it finds.

    Bare hostnames

    WEB_DOMAIN and API_DOMAIN are hostnames only: example.com, not https://example.com, not example.com/, and not example.com:443. Caddy builds the https:// origins from them, and a stray scheme or slash becomes a certificate request for a name that does not exist.

    Values the stack derives for you

    APP_URL, FRONTEND_URL, SANCTUM_STATEFUL_DOMAINS, CORS_ALLOWED_ORIGINS, and both NEXT_PUBLIC_* build arguments are computed from the two domains inside docker-compose.yml, so they cannot fall out of step. Change the domains, not those derived keys.

    NEXT_PUBLIC_* values are compiled into the browser bundle. After changing a domain, rebuild: docker compose up -d --build web.

    Where other credentials live

    Payment gateway keys, the Google OAuth client, and S3 credentials are saved in the admin panel (Settings → Payment Gateways / Social Login / Storage), not in this file. That keeps them changeable without a restart, and secrets are write-only in the panel. See the Admin panel chapter for how to obtain each one.

    Generate strong secrets

    Use a password manager, or generate values on the server with openssl rand -base64 32. Quote values that contain spaces, #, $, or ! — Compose interpolates $ inside unquoted values.

    Email (SMTP)

    The platform sends verification links, password resets, course approval notices, payout decisions, and instructor application results by email. Out of the box MAIL_MAILER=log, which writes each message to the API container log and sends nothing — fine for a smoke test, never for a live site.

    The eight variables that matter

    Key Value
    MAIL_MAILERsmtp
    MAIL_HOSTThe SMTP hostname from your provider's "SMTP settings" page.
    MAIL_PORT587 for STARTTLS (the common choice), 465 for implicit TLS, 25 only if your host allows it.
    MAIL_SCHEMEsmtp for port 587 / STARTTLS; smtps for port 465. Leave empty only when the provider explicitly says no encryption.
    MAIL_USERNAMEUsually the full mailbox address; some providers use a fixed username such as apikey.
    MAIL_PASSWORDThe SMTP password or API key from the provider — not your webmail login when two-factor authentication is on. Gmail requires an App Password.
    MAIL_FROM_ADDRESSThe sender address, e.g. no-reply@example.com. It should be on your own domain and verified with the provider, or messages will be marked as spam.
    MAIL_FROM_NAMEThe sender name, e.g. your academy name. Quote it if it contains spaces.

    Provider values

    Provider Host Port / scheme Notes
    Gmail / Google Workspacesmtp.gmail.com587 / smtpRequires 2-Step Verification and an App Password. The From address must match the account. Not suitable for bulk mail.
    Amazon SESemail-smtp.<region>.amazonaws.com587 / smtpCreate SMTP credentials in the SES console; verify the domain and move out of the sandbox before launch.
    Mailgunsmtp.mailgun.org587 / smtpUsername is the full postmaster address for your domain; password is the SMTP password, not the API key.
    SendGridsmtp.sendgrid.net587 / smtpUsername is literally apikey; password is the API key. Verify the sender domain first.
    Brevosmtp-relay.brevo.com587 / smtpUse the SMTP key from Brevo, not the account password.
    Zoho Mailsmtp.zoho.com587 / smtpUse an app-specific password when 2FA is enabled.

    Apply and test

    After saving .env, recreate the API container so it receives the new values. The first boot seeded the database already, so this is a restart, not a reinstall:

    docker compose up -d api
docker compose logs --tail=20 api

    Then test with a real flow: open https://example.com/forgot-password, request a reset for the administrator address, and check that the message arrives. Mail is queued, and the API container runs the worker, so there is no separate service to start.

    Where to look when mail does not arrive
    • docker compose logs api | grep -i mail — connection refused, authentication failed, or timeout errors appear here.
    • Admin → Settings → General Settings has a contact email; it is shown to visitors, but it is not the SMTP sender. The sender is always MAIL_FROM_ADDRESS.
    • If MAIL_MAILER=log, messages are written to the log and deliberately not delivered. That is the most common reason a test "sends nothing".
    • Check failed_jobs in the database or docker compose logs api for a queue job that exhausted its retries.
    • Gmail and many providers reject a From address that is not verified on the account. SPF, DKIM, and DMARC records for your domain decide whether mail lands in the inbox or in spam.

    Build and start

    cd /opt/lms
docker compose up -d

    The first run builds both images (10–20 minutes on a small server, mostly the Next.js build), waits for MySQL, migrates and seeds the database, then starts Caddy, which requests both certificates. Watch it:

    docker compose ps
docker compose logs -f api caddy

    All four containers should report running (MySQL also healthy), and the Caddy log should end with certificate obtained successfully for each hostname.

    What the first boot does

    1. Generates an application key

      Unless APP_KEY is set, a key is generated and written to storage/app/.app-key on the volume, so later restarts reuse it and encrypted sessions stay valid.

    2. Waits for the database and prepares storage

      The entrypoint polls MySQL until it accepts connections, links public/storage to the public disk, and fixes ownership so nginx and php-fpm can both read uploads.

    3. Migrates every boot, seeds once

      php artisan migrate --force runs on every start, so an updated image also updates an existing installation's schema. Seeding runs only the first time: a marker file storage/app/.installed records it, so restarts never duplicate the starting content or overwrite the administrator.

      The administrator is part of that first seeding: it is created from ADMIN_EMAIL and ADMIN_PASSWORD without a manual command, and the boot log confirms it with Administrator created: ....

    Sign in

    URL What
    https://example.comThe storefront: catalog, course pages, checkout, student and instructor dashboards.
    https://api.example.com/adminThe Filament admin panel. Sign in with ADMIN_EMAIL and ADMIN_PASSWORD.
    https://example.com/api/v1/settingsDataA public API endpoint — a quick health check for the backend.
    https://api.example.com/storage/…Uploaded thumbnails, avatars, and the logo.

    Changing the administrator later

    Seeding only runs once, so editing .env afterwards changes nothing by itself. To move the account to another address, or to recover a forgotten password, set the new values in .env, recreate the API container, and run the seeder again — it updates that account instead of creating a second one:

    docker compose up -d api
docker compose exec api php artisan db:seed --class=AdminSeeder --force

    Use a new ADMIN_EMAIL to add a second administrator; the existing account is left untouched.

    If the frontend build is killed with "signal 9"

    The Next.js build needs roughly 2 GB of RAM on its own. On a 2 GB server add swap before building:

    sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

    HTTPS and certificates

    Caddy is the only container exposed to the internet. It answers on 80 and 443 for both hostnames, redirects plain HTTP to HTTPS, and obtains a Let's Encrypt certificate for each name once DNS resolves. Nothing is bought, copied, or renewed by hand.

    What runs on its own
    Task Handled by
    First certificate for both namesCaddy, within a minute of the stack starting, provided DNS resolves and ports 80/443 reach the server.
    Renewal before the 90 days run outCaddy, roughly 30 days ahead, retrying on its own if an attempt fails.
    HTTP → HTTPSCaddy, for both hostnames.
    Surviving updates and rebootsThe lms-caddy-data volume, which keeps the certificates and the ACME account key.

    Checking issuance and renewal

    # successful orders and failures
docker compose logs caddy | grep -i certificate

# the names currently issued
docker compose exec caddy ls /data/caddy/certificates/acme-v02.api.letsencrypt.org-directory

    A failed order states the reason in that log: DNS not resolving, port unreachable, or a rate limit. Let's Encrypt allows five certificates per name per week, so do not reset the Caddy volume repeatedly.

    Moving to another domain

    Put the new names in .env and rebuild, because the storefront origin is compiled into the browser bundle:

    docker compose up -d --build

    Keep the old DNS records pointing here until the new names answer, so no visitor lands on a hostname without a certificate. Caddy notices the new names and requests their certificates; the old ones stay in the volume and expire unused.

    Certificate-expiry mail (optional)

    Renewal is automatic, so this mail is a safety net. Add your address inside the global block of docker/caddy/Caddyfile and restart Caddy:

    {
	email you@example.com
	admin off
}
    docker compose restart caddy
    Cookies require HTTPS in production

    The image runs with APP_ENV=production, which marks the session cookie Secure. Logins therefore only work over https://; testing through http://SERVER_IP:3000 will appear to succeed and then drop the session. Always test through the domain.

    Day-to-day operations

    Logs and a shell

    docker compose logs -f api web caddy
docker compose exec api php artisan about
docker compose exec api sh

    Application logs go to stderr, so they appear in docker compose logs rather than a file inside the container.

    Where the data lives

    Docker prefixes volume names with the Compose project name (lms), so the volume declared as lms-storage is lms_lms-storage on disk.

    • lms_lms-mysql — the whole database.
    • lms_lms-storage — mounted at /var/www/html/storage: app/public/ (thumbnails, avatars, logos, certificates), app/private/ (lesson videos and attachments), and logs/.
    • lms_lms-caddy-data, lms_lms-caddy-config — certificates and Caddy state. Neither needs backing up; they are reissued if lost.

    Backups

    Back up the database and the storage volume together. A database dump alone restores a site whose courses point at missing videos.

    cd /opt/lms

# database
docker compose exec -T mysql sh -c \
  'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction "$MYSQL_DATABASE"' \
  > "db-$(date +%F).sql"

# uploads, videos, attachments
docker run --rm \
  -v lms_lms-storage:/data:ro \
  -v "$PWD":/backup \
  alpine tar czf "/backup/storage-$(date +%F).tar.gz" -C /data .

    Copy both files off the server. Test a restore on a spare machine before you need it.

    Updating the application

    Replace the code with the new version, keeping .env and the volumes, then rebuild. Migrations run automatically when the API container starts:

    cd /opt/lms
# replace localhost/, frontend/, docker/, docker-compose.yml with the new release
docker compose up -d --build
docker compose ps
docker compose logs --tail=60 api
    Back up before an update

    Take the database and storage backup above first. A migration that removes or rewrites a column cannot be undone by rebuilding the previous image.

    Queue and failed jobs

    The api container runs php artisan queue:work under supervisord, so queued mail and notifications are delivered without any extra service. It restarts by itself and is recycled hourly. To inspect it:

    docker compose exec api ps -ef | grep queue:work
docker compose exec api php artisan queue:failed
docker compose exec api php artisan queue:retry all

    Media on a bucket

    Lesson videos can stay on the storage volume or move to an S3-compatible bucket. The switch is made in Admin → Settings → Storage, with a connection test before you commit. Existing files are not moved automatically — copy them with the included command:

    docker compose exec api php artisan media:migrate-to-cloud --target=s3

    The bucket must stay private. The API streams the bytes itself or redirects to a short-lived signed URL; a public bucket would let anyone download a course.

    Troubleshooting

    Symptom Cause and fix
    Compose refuses to start and prints ADMIN_EMAIL is required .env is missing or was created in the wrong folder. It must sit next to docker-compose.yml.
    The home page loads but every section is empty The API container is not healthy. docker compose logs --tail=100 api shows the migration or boot error.
    Caddy reports a certificate failure DNS does not point at this server, or ports 80/443 are blocked or owned by another process. Check with dig +short and sudo ss -ltnp | grep -E ':80|:443'.
    Login seems to succeed, then drops the session You are testing over plain HTTP or through the IP instead of the domain. Production cookies are Secure; use https://example.com.
    Sign-in returns 419 The storefront origin does not match WEB_DOMAIN, or the web image was built before the domain was changed. Rebuild with docker compose up -d --build.
    No email arrives Check MAIL_MAILER (log sends nothing), the SMTP credentials, and the API log. See Email (SMTP).
    Uploads fail with a 500 or a permission error The storage volume is full, or its ownership was changed by hand. df -h and docker compose logs api first; avoid chown inside the volume unless you know the container's UID.
    The build is killed with exit code 137 The server ran out of memory during the Next.js build. Add swap (see above) or build on a larger machine.
