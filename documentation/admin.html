    Admin panel

    The control room. Every screen in the panel, in the order the sidebar presents it, with what each field does, where the result appears on the storefront, and — for the settings that need an outside account — exactly where to obtain the keys.

    Nine sections: this overview, then the eight sidebar groups — Orders and Payments share one section. The last section is the longest on purpose: gateways, Google sign-in, and object storage are the three places an installation is most often misconfigured.

    The panel at a glance

    The panel is served by the Laravel application at https://api.example.com/admin. It is a Filament application: tables search, sort and filter on the columns that matter, list screens offer bulk actions where they make sense, and every form validates before it saves. Only users with the administrator role can open it.

    The dashboard

    The first screen answers "is anything waiting for me?" before it shows anything else.

    Widget Shows

    Paid OrdersHow many orders reached paid.
    Active InstructorsAccounts with the instructor role whose user account is active.
    Pending Payout RequestsA count that links straight to the withdrawal queue.
    Instructor ApplicationsA count that links to the applications waiting for a decision.
    Sales trendRevenue over time across the whole marketplace.
    Top instructorsWho is earning the most.

    Conventions that apply everywhere

    • Secret fields survive a blank save. Credentials render masked and can be revealed in place by an administrator; saving a field blank keeps the stored secret. Type a new value only when you mean to replace it, because the old one cannot be recovered afterwards.
    • Saved settings take effect immediately. Gateway, Google, and storage values are read from the database on every request, so there is no deploy and no restart.
    • Deletes are permanent. There is no trash can for most resources. Deleting a course with enrolled students is refused by the API, but the panel's delete action should still be treated as final.
    • The audit log records what you do. Every panel visit and every create, update, or delete is written to the admin_audit log channel with the administrator's identity, IP, URL, and submitted input. Password, token, secret, and key fields are redacted first.

    Courses

    Five screens cover the catalog, the two review queues, and who is enrolled in what. Before reading them, keep three independent ideas apart — they are the source of most confusion:

    Idea Field Values Meaning
    Approval approval_status draft, pending_approval, approved, rejected Whether the course has passed review. Only approved courses can appear in the catalog.
    Publication is_active on / off The "Active" toggle on the course form. An approved course is visible only when this is on.
    Lifecycle status ongoing, completed Whether teaching is still running. It is not draft/published, and it controls certificate eligibility: no certificate is issued while a course is ongoing.

    Categories

    The catalog's taxonomy. Every course belongs to exactly one category.

    • Fields — parent category (optional, top-level categories only), name, slug, description.
    • Where it appears — the category filter on /courses, the category cards on the homepage, and a public page at /categories/{slug}. The order is the one set in the list.
    • Practical note — a course cannot be saved without a category, so create the taxonomy before importing courses. Renaming a category changes its label everywhere; changing its slug changes the public URL.

    Courses

    The full catalog with instructor, category, price, lifecycle status, approval state, and the Active toggle. The row action is Edit; bulk delete is available for courses that no longer have students.

    Field What it controls
    Category, InstructorOwnership and taxonomy. The instructor list contains accounts with the instructor or admin role.
    Title, SlugThe public name and URL, at /courses/{slug}. The slug auto-fills from the title but can be edited.
    ThumbnailCard and course-page image. Stored on the public disk.
    Preview videoThe public trailer. Stored on the private lesson disk and streamed only through the preview endpoint.
    Short description, DescriptionCard summary and the rich-text body on the Overview tab.
    Requirements, Objectives, TagsLists shown on the course page and used by catalog search.
    Price, Discount priceList price and the lower price a student actually pays. The discount must be below the list price.
    StatusOngoing while lessons are still being added; Completed when the course is finished. Marking a course completed is what unlocks certificate issuance for students who already met the requirements.
    Level, LanguageCatalog filters and course metadata.
    ActivePublication switch. Off hides an otherwise approved course without deleting it.
    A course added in the panel starts as a draft

    The panel's create form is a data-entry tool, not a shortcut around review: a new row begins at draft and therefore does not appear in the catalog. The review queue only lists courses that were explicitly submitted by an instructor, so the normal publishing path is: the instructor creates and submits, and you approve it in Course Approvals. Use the panel's create form only when you have a plan for that course's approval state.

    Course Approvals

    The queue of submitted courses — drafts are deliberately excluded. Open a row for a decision snapshot: thumbnail, instructor, category, price, discount, level, language, section and lesson counts, enrollment and instructor revenue, plus the short description, full description, and trailer. The curriculum itself is one click away through Open this course in the admin editor. Two actions decide it:

    • Approve — sets the approval to approved, turns is_active on, and emails plus notifies the instructor. The course is on sale immediately.
    • Reject — requires a reason (3–2000 characters). The reason is emailed and shown in the instructor's editor; the course returns to the instructor for changes.

    The list refreshes itself every 30 seconds, and the sidebar badge counts pending submissions. Courses already approved stay in the list for reference; the Status filter narrows it to Pending when you are working the queue.

    Course Edit Requests

    Once a course is live, the instructor may not silently change what students bought. Changes to title, price, discount price, level, language, category, thumbnail, and preview video are collected into a single pending request instead of being applied.

    • Each request lists the affected fields with the current and proposed values, and any proposed trailer can be played beside the live one.
    • Approving applies the whole batch, deletes the replaced media file, and notifies the instructor.
    • Rejecting requires a reason, keeps the live course exactly as it was, deletes the uploaded replacement media, and notifies the instructor.
    • While a request is pending the course stays approved and on sale. Pending changes from the same instructor merge into one request; reverting a field removes it from the batch.

    Non-sensitive edits — description, objectives, requirements, tags, curriculum, and the ongoing/completed lifecycle — are applied immediately and never enter this queue.

    Enrollments

    The student-to-course links that decide who may watch what. Each row shows the student, course, payment, status (active, completed, canceled), and progress percentage. The video, attachment, quiz, and certificate endpoints all check this record.

    Use it to correct access after a refund or a support mistake: setting the status to canceled removes access; creating a row grants it. Deleting an enrollment removes the student's progress record's authorization even though the lesson progress rows remain in the database.

    Private media previews

    Lesson videos and trailers live on a private disk and have no public URL. The panel can still play them: the course detail and approval screens show the trailer, and the lesson relation managers show the uploaded video. Playback is authorized by the admin session, so a copied URL does not work for anyone else.

    Users

    Three lists, split by what the administrator needs: all accounts, the teaching side, and the people who want to join it.

    All Users

    Search and edit any account. The form edits name, email, and (on create) password; the list also shows each account's role and creation date. Delete is available for accounts that should be removed entirely.

    Roles are granted by workflow, not by this form

    The user edit screen does not expose a role selector in this version. A student becomes an instructor through Instructor Applications → Approve, which sets the role and creates the teaching profile in one transaction. If a role must be changed by hand, do it in the database with care: an instructor without an instructor profile cannot use the teaching workspace.

    All Instructors

    Every account with the instructor or admin role, with its teaching profile attached as a relation. The profile record is the part that matters:

    Profile field / action Effect
    Bio, Expertise, Social linksShown on the public instructor directory and the Instructor tab of every course they teach.
    RatingThe average used in the directory. It is maintained by the platform, not typed by hand.
    Status: activeFull access to the teaching workspace.
    Status: bannedLocks the teaching workspace — no new or edited courses — while existing courses stay visible. Reversible with Restore to Active.
    Status: rejectedBlocks sign-in and hides all of their courses from the public site. Also reversible from this screen.
    View ProfileReads the bio, expertise, rating, and links in a modal without opening the editor.

    The profile form stores social links as a JSON object, so enter them as valid JSON ({"website":"https://…"}) when editing the raw field.

    Instructor Applications

    Applications submitted from the storefront, with the applicant's bio, expertise, links, and status. View opens the full pitch without leaving the list.

    • Approve — turns the account into an instructor, creates the teaching profile from the application, marks the application approved, and sends an email plus an in-app notification with a link to the teaching workspace.
    • Reject — records a note (up to 1000 characters) that the applicant sees on Become an instructor, and sends an email. The applicant can edit the form and apply again; an approved application is not re-reviewed.

    Applicants keep their student access while they wait, so a slow review never blocks their learning.

    Orders and payments

    Three screens: what was bought, whether it was paid, and what the site owes its instructors.

    Orders

    One row per checkout with the customer, order number, total, discount, coupon, payment method, and status. Open a row to see its items. The status cell is editable in place:

    pendingThe order exists but no settled payment is attached.
    paidPayment settled; enrollments and instructor earnings were created.
    completedA legacy status kept for old records.
    canceledThe attempt was abandoned or closed.
    Changing an order status by hand does not enroll anyone

    Enrollment and earnings are created by the payment finalizer, not by the order row. If a payment really settled, use Payments → Resync so the whole chain runs again. Editing the status is only for correcting the record.

    Payments

    The gateway-side view of the same money: user, amount, gateway, status, gateway reference, transaction id, order, coupon, and how the payment was verified (webhook, success page, resync, free checkout).

    • Resync — asks the gateway what actually happened. A paid session is finalized (order paid, enrollments granted, earnings recorded); an unpaid one is canceled. Resync is also available for several selected rows at once.
    • Cancel locally — marks a pending payment and its order canceled without asking the gateway. Use it only when the gateway is unreachable; resync is the safe default.

    The gateway badge and the Verified Via column together explain almost every support question about access. A pending Stripe session with a missing webhook secret, for example, stays pending until a resync or a fixed webhook resolves it.

    Payout Requests

    The instructor withdrawal queue. Each row shows the instructor, total earnings, available earnings, other pending payouts, the requested amount, the payment details they entered, and the status.

    1. Approve

      Confirms the reservation the request already placed against the instructor's earnings and notifies them. Nothing is transferred; the amount stays in the pending total.

    2. Pay out of band

      Send the money by the method in Payment Details — a bank transfer, PayPal, Wise, or whatever methods you configured. The panel does not move money.

    3. Mark Paid

      Completes the request, records the payment date, moves the amount from the instructor's pending total to paid, and notifies them.

    4. Or reject with a reason

      The reservation is released back to available earnings and the instructor is told why. They can request again.

    Partial requests are intentional

    An instructor can request any amount at or above the minimum and at most their available balance. The request is allocated across their oldest available earnings, and anything left on an earning stays available for a later request.

    Coupons

    Discount codes and the evidence of who used them.

    Coupons

    Field Meaning
    CodeWhat the student types at checkout. Keep it short and unambiguous.
    Title, DescriptionInternal labels, shown in the panel and in some checkout messages.
    Typepercent takes a percentage of the cart; fixed takes an amount off.
    AmountThe percentage (0–100) or the fixed value, depending on the type.
    Usage limitTotal redemptions across the site. Empty means unlimited.
    Minimum order amountThe cart total required before the code applies.
    Start date, End dateThe active window. Both are required.
    ActiveAn off switch that keeps the code and its history.
    First order onlyRestricts the code to customers with no previous purchase.

    A code is validated again on the server at checkout, so editing or deactivating one takes effect immediately. A 100% coupon produces a zero-total order, which enrolls without touching a gateway.

    Coupon Usages

    One row per redemption, linked to the coupon, the customer, and the payment. This is the list to consult when someone claims a code did not work or has already been used. The rows are written by checkout; treat them as an audit trail.

    Certificates and quizzes

    Certificates students have earned, and the quizzes that unlock them.

    How a certificate is earned

    Issuance is automatic and idempotent — there is no "issue certificate" button. A student receives one only when all of the following are true:

    1. The course's lifecycle status is completed. While it is ongoing, a student at 100% is not eligible, because the instructor may still add lessons.
    2. The student has an active or completed enrollment.
    3. Every lesson in the course is marked completed.
    4. Every active quiz has been passed at least once.
    5. Certificates are enabled in General Settings.

    When an instructor marks a course completed, the platform walks its enrollments and issues certificates to everyone who already met the other conditions. A revoked certificate can be re-earned with a new serial and code after the student re-qualifies.

    Certificates

    Every issued certificate with its serial, public verification code, student, course, status, and issue date. Open one for the full record and three actions:

    • Download PDF — the same A4 landscape document the student downloads. Only available while the certificate is valid.
    • Revoke — requires a reason (3–500 characters), stored for audit and shown on the public verification page. The student can no longer download it.
    • Restore — clears the revocation when it was made in error.

    The public page at /certificates/{code} needs no account: anyone can verify a serial and see whether it is valid or revoked. The snapshot stored at issuance (student name, course title, instructor, site name) is what the PDF prints, so renaming a course later cannot alter an old certificate.

    Quizzes

    One quiz per course, written by the instructor. The panel can supervise its settings but not create a second quiz for a course:

    Quiz ActiveInactive quizzes are hidden from students and block certificate issuance.
    Pass Mark (%)0 means "use the global default" from General Settings. Only an administrator can change it, which keeps a failing student from pressuring an instructor into lowering the bar.
    Max AttemptsEmpty means unlimited.
    Questions and optionsRead-only in the panel's view screen; editable by the instructor in the course editor. Each question can carry points and an explanation shown in the marked review.

    Content

    Everything a visitor reads on the public site — including the text you are legally answerable for — is written here rather than in code. Changes appear on the storefront immediately; the homepage is rebuilt per request.

    Homepage Content

    The landing page is assembled from seven rows, one per section. Each row has a Show this section toggle and its own fields; the order of the page is fixed, not drag-and-drop.

    Section Fields What appears on the storefront
    hero Title, highlight, subtitle, badge, search placeholder, and two optional hero course cards. The first screen: gradient headline, search box, category shortcuts, and two floating course cards. Leave the cards empty to fall back to the most popular courses.
    features_strip Three items, each with a title, subtitle, and icon. The three small assurances directly under the hero.
    popular Title, subtitle, badge (the "view all" label). The featured bento grid of popular courses, ordered by enrollment velocity.
    latest_courses Title, subtitle, badge. Newest approved courses.
    instructors Title, subtitle, badge. Top instructors by rating and sales.
    blog Title, subtitle, badge. The three latest published posts.
    call Title, subtitle, trust line, two buttons (text and link each). The closing call-to-action panel.

    Each row exposes exactly the fields that section renders; a section left without custom copy still uses its built-in wording. Turning every section off leaves an empty page, which is a quick way to check whether a problem is content or code.

    Footer

    The footer is a single configuration row. Edit it rather than adding rows; creation and deletion are disabled on purpose.

    • About text — the short paragraph next to the logo; the site name is prepended automatically.
    • Copyright line — shown after © and the current year.
    • Quick links — reorderable label/URL pairs. Internal paths such as /courses or full URLs are both accepted.
    • Social media links — platform (Facebook, Instagram, X, LinkedIn, YouTube, Telegram, GitHub, TikTok), accessibility label, and URL. The platform chooses the icon.
    • Show footer — the on/off switch for the whole block.

    Terms & Privacy

    Two independent documents on one screen, each with its own page title and rich-text body. The terms render at /terms and the privacy policy at /privacy-policy, linked from the footer and the cookie banner. They stay editable without a deploy — but they are your legal text, not a template: have counsel review them before launch.

    Cookie Consent

    The first-visit banner: title, body, the labels of the two buttons (accept all, necessary only), and the label of the policy link. The cookie policy page at /cookie-policy renders the same body text, so the copy lives in one place. The visitor's choice is remembered in the browser; the banner does not reappear until storage is cleared.

    Blog

    Posts appear at /blog, at /blog/{slug}, and as the homepage's blog section.

    Title, SlugThe headline and the public URL. The slug auto-fills from the title.
    ExcerptSummary on cards and in search results, up to 500 characters.
    Cover imageOptional; used on cards, the post page, and link previews.
    ContentThe rich-text body.
    StatusDraft is invisible; Published is live.
    Publish dateEmpty publishes on save. A future date schedules the post.

    Communication

    Reaching students, and answering them.

    Send Notifications

    Compose an in-app notification for one user or for everyone.

    • Recipient — leave empty to send to every student and instructor. The list only contains those two roles; administrators are not spammed by a broadcast.
    • Title and message — the text shown in the bell menu and on /dashboard/notifications.
    • Type — info (blue), success (green), warning (yellow), or danger (red); it changes the badge color, not the delivery.
    These are in-app only

    Sending a notification does not send an email. Course approval, rejection, payout, and application decisions send both an email and an in-app notification; a manual broadcast is in-app only.

    Support Tickets

    The student support queue: subject, user, priority, status, reply count, and date. The default filter is open tickets. Clicking a row opens the full conversation with the student's messages and every staff reply.

    • Reply — adds a message to the thread, visible to the student immediately.
    • Close Ticket — marks it closed; the student sees the resolution and cannot add messages to a closed thread from the dashboard.
    • Reopen — returns it to the open queue if the problem comes back.

    Priority is set by the student when opening the ticket (low, normal, high) and helps order the queue; it does not change notifications.

    Settings

    Six pages that decide how the whole installation behaves. Everything here is saved to the database and read on the next request — no restart, no deploy, no file editing. Credentials saved here take priority over the fallback values in .env.

    General Settings

    Site namePage titles, the panel brand, the footer, and issued certificates. This is the name visitors see; APP_NAME in .env is only a fallback for the backend.
    Contact emailThe site's public contact address, exposed to the storefront with the other settings. It is not the SMTP sender — that is MAIL_FROM_ADDRESS.
    LogoThe panel sidebar brand, the storefront navbar and footer, the dashboard brand, and the social-preview image. PNG or SVG with a transparent background works best; the old file is deleted when you replace it.
    FaviconThe browser-tab icon, also used by the panel. Square PNG, 64×64 or larger.
    Default Quiz Pass Mark (%)Used by every quiz whose pass mark is left at 0. Changing it affects those quizzes immediately.
    Enable CertificatesThe master switch. When off, no certificate is issued and the eligibility endpoint returns false, even for a completed course that satisfies every other rule. Existing certificates stay downloadable.

    Payment Gateways

    Four gateways, each with its own switch and credential fields. An enabled gateway is offered at checkout, so fill its fields before you switch it on; an incomplete gateway fails at the payment step instead of quietly disappearing. Stripe behaves differently: a saved secret key is what offers it at checkout, and its switch is informational. The buttons appear in the order Stripe, PayPal, Mollie, Razorpay. Credentials are stored in the database, not in .env. Secret fields render masked and can be revealed in place; saving one blank keeps the stored secret.

    Before configuring a gateway, decide the site currency. Checkout charges in the site currency (seeded as USD); a gateway only accepts the currencies enabled on your merchant account.

    Stripe (cards)

    1. Get the secret key

      In the Stripe Dashboard, switch off Test mode for a live site, then open Developers → API keys. Copy the Secret key (sk_live_… or sk_test_…). The publishable key is not used by this integration.

    2. Paste it into the panel

      Settings → Payment Gateways → Stripe Secret Key. Save it. A stored secret key is what makes Stripe available at checkout — the Enable Stripe switch is informational — so paste a live key only when you are ready to sell. The field shows the saved key masked, and leaving it blank keeps it.

    3. Create the webhook

      In Developers → Webhooks, add an endpoint for:

      https://api.example.com/api/v1/webhooks/stripe

      Replace api.example.com with your API_DOMAIN. Select these events:

      • checkout.session.completed
      • checkout.session.async_payment_succeeded
      • checkout.session.async_payment_failed
      • checkout.session.expired

    4. Paste the signing secret

      Open the new endpoint, reveal its Signing secret (whsec_…), and save it in Stripe Webhook Signing Secret. Without it the endpoint rejects every call with a 400 and logs Webhook signing secret is not configured.

    What happens at checkout. The API creates a Stripe Checkout Session and redirects the browser to Stripe. On return, the success page verifies the session; the webhook does the same server-to-server. Both paths run the same idempotent finalizer, so an order is never enrolled twice. A failed or expired session cancels the pending payment. If a webhook was missed, Payments → Resync asks Stripe again.

    PayPal

    1. Create a REST app

      Sign in at developer.paypal.com, open Apps & Credentials → Apps & Credentials, choose Live or Sandbox, and create an app (type: Merchant). Copy its Client ID and Secret.

    2. Fill the four fields

      Enable PayPal, Mode (live or sandbox — it must match where the keys came from), Client ID, and Client Secret. Save.

    What happens at checkout. The API creates a PayPal order through the REST Orders API and redirects to PayPal's approval page. On return the server captures the order; only a completed capture marks the payment paid. Replaying a captured order is idempotent, so a refresh cannot double-charge. No webhook endpoint has to be registered.

    Mollie

    1. Create an API key

      In the Mollie dashboard, open Developers → API keys. Use the Live key for production or the Test key while setting up. Copy it (live_… / test_…).

    2. Paste and enable

      Enable Mollie, paste the key into Mollie API Key, and save.

    What happens at checkout. Mollie hosts the payment page (iDEAL, cards, and the methods enabled on your Mollie account). On return, the API asks Mollie for the payment's real status — only paid finalizes the order. The status is never taken from the browser, and no webhook registration is needed. If the buyer closes the tab before returning, the payment stays pending; settle it with Payments → Resync.

    Razorpay

    1. Generate API keys

      In the Razorpay Dashboard, open Account & Settings → API Keys (in test mode: Settings → API Keys) and generate a key. Copy the Key ID (rzp_live_… / rzp_test_…) and the Key Secret shown once.

    2. Paste and enable

      Enable Razorpay, fill Key ID and Key Secret, and save. Both fields are required; the gateway is offered only when both are present.

    What happens at checkout. The API creates a Razorpay order and the storefront opens the Razorpay Checkout modal. The browser returns with a payment id and an HMAC signature; the server verifies the signature, then fetches the order's payments and finalizes only a captured payment. No redirect URL or webhook is needed.

    Test with the smallest real purchase

    Configure one gateway first, make a low-priced course, buy it with a real (or sandbox) card, and confirm four things: the order becomes paid, the course appears in the student's dashboard, the payment shows verified_via, and the instructor's earning appears in Payout Requests context. Then repeat with a coupon and with a failed payment.

    Payout Methods

    Two things on one screen: the commercial rules and the withdrawal methods instructors may choose.

    • Instructor commission (%) — the site's share of every sale. It is copied onto each earning at the moment of sale, so changing the rate never rewrites past earnings.
    • Minimum payout amount — below this, the instructor's request form refuses the amount and states the threshold.
    • Methods — a reorderable list of three fields: Key (a stable identifier such as bank_transfer), Display name (what the instructor sees), and Account hint (the placeholder that tells them what to enter, e.g. "IBAN and account holder").

    Removing a method hides it from future requests; requests already submitted keep the details they stored. The defaults are bank transfer, PayPal, and Wise; edit them to match how you actually pay.

    Social Login

    Google sign-in. The button appears on the login and register pages only when Enable Login with Google is on and both credentials are saved. Save the credentials first, then enable the switch.

    1. Create a Google Cloud project

      Open the Google Cloud Console, create or select a project, and open APIs & Services → OAuth consent screen. Choose External, fill the app name, user support email, and developer contact, and add your storefront domain as an authorized domain.

    2. Create the OAuth client

      Go to APIs & Services → Credentials → Create credentials → OAuth client ID. Application type: Web application.

      Under Authorized JavaScript origins, add the storefront origin:

      https://example.com

      Under Authorized redirect URIs, add the URI shown on the Social Login screen. With the Docker stack it is:

      https://example.com/auth/google/callback

      Copy it from the panel rather than typing it from memory, and do not confuse it with the storefront's own /auth/callback page, which is where the browser lands after the backend finishes.

    3. Paste the credentials

      Copy the Client ID and Client secret into the same screen, enable the toggle, and save. Changes are picked up on the next sign-in attempt.

    What happens when a visitor uses it. The button navigates to the API's OAuth start route, Google returns to the callback above, and the API creates or finds the account and starts a normal session. If the Google email already belongs to a password account, the visitor is told to sign in with the password and link Google from the profile instead of silently merging two identities. From Profile → Connected accounts a signed-in user can link or unlink Google; unlinking is refused when it would leave no way to sign in.

    Testing and publishing the consent screen

    While the Google consent screen is in Testing, only test users you list can sign in. Publish it before launch. The redirect URI must match exactly — scheme, host, path, and no trailing slash.

    Storage

    Where lesson videos, trailers, and attachments live, and how their bytes reach the browser.

    Delivery choices

    Field Options Effect
    Lesson Video Disk private, public, videos, s3 private is the safe default: files sit on the server's private storage. s3 sends new uploads to the bucket. public and videos are local disks that can be served directly — avoid them for paid content.
    Video Serving Mode proxy, signed proxy streams bytes through PHP after checking enrollment. signed redirects to a time-limited bucket URL, so bandwidth goes straight from the bucket to the viewer; it falls back to proxying when the disk cannot sign URLs.
    The bucket must stay private

    Do not enable public access or attach a public base URL to the bucket. A public bucket turns every lesson into a downloadable file for anyone who guesses a path. Signed mode still requires the objects themselves to be private.

    S3 / cloud credentials

    Turn on Enable S3 / cloud storage first — while it is off, the panel's storage values are ignored and the .env values apply. Then fill:

    Access Key IDThe key from your provider (AWS IAM access key, R2 token access key, Spaces key, MinIO user).
    Secret Access KeyIts secret. Write-only in the panel.
    Regionus-east-1, eu-west-1, auto for R2, and so on, as required by the provider.
    BucketThe exact bucket name, not its URL.
    Custom URL / CDN baseOptional. Used to build file links when a CDN sits in front of the bucket.
    Custom endpointRequired for non-AWS providers: R2, Wasabi, MinIO, Spaces. Leave empty for AWS S3.
    Use path-style endpointEnable for MinIO or any provider that needs the bucket in the path instead of the hostname.

    Provider recipes

    Provider Where the keys come from Endpoint / region
    AWS S3 IAM → Users → create a user with programmatic access and an inline policy for the bucket (s3:GetObject, PutObject, DeleteObject, ListBucket). Copy the access key pair. Endpoint empty; region as created (e.g. eu-west-1).
    Cloudflare R2 R2 → Manage R2 API Tokens → Create token with Object Read & Write for the bucket. The token gives the Access Key ID and Secret. https://<account-id>.r2.cloudflarestorage.com; region auto.
    DigitalOcean Spaces API → Spaces Keys → Create access key. https://<region>.digitaloceanspaces.com; region as created.
    Wasabi Console → Access Keys → Create access key. https://s3.<region>.wasabisys.com; matching region.
    MinIO A user and its access/secret key; create the bucket in the MinIO console. Your MinIO URL; path-style endpoint on.

    The safe order to enable it

    1. Save the credentials and test

      Fill the key fields, leave Lesson Video Disk on private, save, then press Test Connection. It uses exactly what a save would store, including unsaved edits. A failure names the bucket, endpoint, or permission that went wrong.

    2. Switch the disk

      Once the test passes, set Lesson Video Disk to s3, choose proxy or signed, and save. New uploads go to the bucket.

    3. Move existing files

      Existing media is not moved automatically. Run the included command from the server:

      docker compose exec api php artisan media:migrate-to-cloud --target=s3

      Then open Storage Report to confirm what is on each disk. A lesson whose file is still local keeps working: the platform records which disk holds each file.

    How the values are resolved

    When the S3 toggle is on, every non-empty panel field overrides the matching AWS_* value from .env; an empty field falls back to the environment. When the toggle is off, the panel's storage block is ignored entirely. The panel is the intended place to change storage, because it also drives the test button.

    Storage Report

    A read-only account of stored media: how much is on each disk, how it is distributed across courses and lessons, and which rows have no disk recorded yet ("legacy" files). Refresh it after a migration to confirm the move, and use it to spot a course whose video is still on the old local disk before you delete that disk.
