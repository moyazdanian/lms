    Deploy to a server

    Everything needed to move the platform from a laptop to a real host with a domain and HTTPS: two DNS records, Docker on the server, the two domain values that must change, the Caddy proxy that ships with the stack — certificates and renewal included — and the checks that prove the site really works.

    This chapter assumes the Docker stack from Docker deployment. A manual PHP install works the same way — only the reverse-proxy targets change.

    What you need before starting

    Minimum for a real course site
    Item Details
    Server Ubuntu 22.04 or 24.04 LTS (any Linux with Docker works). 2 vCPU and 2 GB RAM minimum; 4 GB makes the first build comfortable.
    Disk 40 GB minimum. Lesson videos are the real cost — if they will be large, plan an S3-compatible bucket instead (Admin → Settings → Storage).
    Domain One domain you control, with the ability to add A records. Two hostnames are used: the storefront and the API.
    Ports 80 and 443 open on the server, answered by the Caddy container. The app containers stay on loopback ports behind it.
    Access SSH with a sudo-capable user. No panel, no PHP, no MySQL on the host — Docker provides all of it.
    Why two hostnames

    The storefront is a Node server and the API (with the admin panel) is nginx + PHP. They also use overlapping paths — the admin panel loads its CSS and JavaScript from /css and /js, which would collide with the storefront if both lived on one hostname. Two hostnames, one certificate each, no path juggling:

    • example.com → the storefront
    • api.example.com → the API, /admin, /storage, webhooks

    The browser talks to the storefront, which forwards /api and /sanctum to Laravel on that same origin — that is what keeps Sanctum's session and CSRF cookies first-party. Uploaded files, the admin panel and webhooks go straight to the API host. The storefront's own server-side rendering uses the private Docker network, so no request loops back through the proxy.

    Point the domain at the server

    At your DNS provider, create these records with the server's public IPv4 address (and AAAA records if you have IPv6):

    Type Name Value Purpose
    A@203.0.113.10The storefront at https://example.com. Use www instead if that is the address visitors should type — pick one.
    Aapi203.0.113.10The API and admin panel at https://api.example.com.

    Verify before touching the server — certificate issuance fails while DNS is still propagating:

    dig +short example.com
dig +short api.example.com

    Both commands must print the server's IP. Propagation is usually minutes, occasionally a few hours.

    Prepare the server

    1. Install Docker Engine and Compose

      sudo apt update && sudo apt upgrade -y
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker "$USER"

      Log out and back in so the group applies, then check:

      docker version
docker compose version

    2. Open only the ports you need

      sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
      Nothing else may own port 80 or 443

      Caddy inside the stack publishes those two ports, and Docker writes its own firewall rules for them, so ufw deny 8080 does not hide a published port. The API and storefront ports are already bound to 127.0.0.1 and are never public. If Apache, nginx or a hosting panel already listens on 80/443, stop it first — sudo ss -ltnp | grep -E ':80|:443' shows which process owns them.

    3. Put the project on the server

      sudo mkdir -p /opt/lms
sudo chown "$USER":"$USER" /opt/lms
# upload the download (scp, rsync or the host's file manager) into /opt/lms
cd /opt/lms
ls docker-compose.yml .env.docker.example

    Configure the stack

    Create the environment file from the shipped example and open it:

    cd /opt/lms
cp .env.docker.example .env
nano .env
    Values that must change for a public site
    Key Set it to Why
    WEB_DOMAIN example.com The storefront host — the address visitors type, and the one Caddy gets a certificate for. Baked into the frontend image at build time.
    API_DOMAIN api.example.com The API and admin-panel host: /admin, uploads, Google callbacks and payment webhooks. Its certificate is issued separately.
    ADMIN_EMAIL, ADMIN_PASSWORD your own credentials The first administrator, created once when the database is seeded. Both are required: nothing is generated and no account is shipped, so compose refuses to start while either is empty.
    DB_DATABASE, DB_USERNAME, DB_PASSWORD, DB_ROOT_PASSWORD long random values Used when MySQL initialises its volume. Change them before the first start; changing them later needs matching changes inside the server.
    MAIL_MAILER + MAIL_HOST, MAIL_PORT, MAIL_USERNAME, MAIL_PASSWORD, MAIL_FROM_ADDRESS smtp and your provider's values Verification and password-reset mail. With log the mail is only written to the container log. 
    WEB_DOMAIN=example.com
API_DOMAIN=api.example.com

ADMIN_EMAIL=owner@example.com
# Required. There is no default account and no generated password.
ADMIN_PASSWORD=a-long-unique-password

DB_DATABASE=lms
DB_USERNAME=lms
DB_PASSWORD=a-long-random-database-password
DB_ROOT_PASSWORD=another-long-random-password

MAIL_MAILER=smtp
MAIL_HOST=smtp.yourprovider.com
MAIL_PORT=587
MAIL_SCHEME=smtp
MAIL_USERNAME=postmaster@example.com
MAIL_PASSWORD=your-smtp-password
MAIL_FROM_ADDRESS=no-reply@example.com
    Bare hostnames

    WEB_DOMAIN and API_DOMAIN are hostnames only: example.com, not https://example.com, not example.com/ and not example.com:443. Caddy builds the https:// origins from them, and a stray scheme or slash becomes a certificate request for a name that does not exist.

    Values the stack fills in

    APP_URL, FRONTEND_URL, SANCTUM_STATEFUL_DOMAINS, CORS_ALLOWED_ORIGINS and both NEXT_PUBLIC_* build arguments are computed from the two domains inside docker-compose.yml. Leave API_PORT and WEB_PORT at 8080 and 3000: they are loopback debugging ports, not public ones. Do not set APP_KEY — it is generated on the first boot and kept on the storage volume, which is what keeps existing sessions and encrypted values readable after an update.

    Build and start

    The API and storefront ports are already bound to 127.0.0.1, so Caddy on ports 80 and 443 is the only public entry point. Build and start everything:

    docker compose up -d

    The first build takes 10–20 minutes on a small server (npm install plus the Next.js production build). Watch the first boot with:

    docker compose ps
docker compose logs -f api caddy

    You should see the database wait, then Running migrations..., then First boot: seeding the database..., then PHP-FPM and nginx start. All four containers must report running (or healthy for MySQL), and the Caddy log ends with certificate obtained successfully for each hostname. Nothing on the host listens on 80 or 443 before this point, which is why an existing web server has to be stopped first.

    If the frontend build is killed with "signal 9"

    The Next.js build needs roughly 2 GB of RAM on its own. On a 2 GB server add swap before building:

    sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

    Certificates and HTTPS

    The stack serves HTTPS by itself: a Caddy container owns ports 80 and 443, answers for both hostnames, redirects plain HTTP to HTTPS, and obtains a Let's Encrypt certificate for each name. There is no certificate to buy or copy, and no cron job to install.

    What runs on its own
    Task Handled by
    The first certificate for example.com and api.example.comCaddy, within a minute of the stack starting — provided DNS resolves and ports 80/443 reach the server.
    Renewal before the 90 days run outCaddy, roughly 30 days ahead, retrying on its own if an attempt fails.
    Surviving updates and rebootsThe lms-caddy-data volume, which keeps the certificates and the ACME account key.
    HTTP → HTTPSCaddy, for both hostnames.

    Checking issuance and renewal

    docker compose logs caddy | grep -i certificate
docker compose exec caddy ls /data/caddy/certificates/acme-v02.api.letsencrypt.org-directory

    The first command is where to look when something is wrong: it prints the order, the challenge and, on failure, the reason — DNS not resolving, port unreachable, or a rate limit. The second lists the names that are currently issued.

    Changing or moving a domain

    Put the new names in .env and rebuild, because the storefront origin is compiled into the browser bundle:

    docker compose up -d --build

    Caddy notices the new names, requests their certificates, and leaves the old ones in the volume to expire. Keep the old DNS records pointing here until the new names answer, so no visitor lands on a hostname without a certificate. If a name used to be served by another machine and the order keeps failing, reset only Caddy's volume — the database and uploads live elsewhere:

    docker compose down
docker volume rm lms_lms-caddy-data
docker compose up -d

    Let's Encrypt issues at most five certificates per name per week, so do that only when the log actually shows a failed order.

    Certificate expiry mail

    Renewal is automatic, so the mail is a safety net rather than a requirement. To receive it, add your address as the first line inside the global block of docker/caddy/Caddyfile:

    {
	email you@example.com
	admin off
}
    docker compose restart caddy

    Using your own proxy instead

    If the server already runs nginx, Apache or Traefik, stop the bundled proxy — and remove its service from docker-compose.yml so a later start does not bring it back:

    docker compose stop caddy

    Forward the storefront domain to 127.0.0.1:3000 and the API domain to 127.0.0.1:8080. One extra rule is required: on the storefront host, /api and /sanctum must reach the API too, which is what keeps Sanctum's session and CSRF cookies first-party. With nginx:

    server {
    listen 443 ssl http2;
    server_name example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /sanctum/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

server {
    listen 443 ssl http2;
    server_name api.example.com;

    ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;

    client_max_body_size 1024m;
    proxy_read_timeout   600s;
    proxy_send_timeout   600s;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

    Create the certificates with sudo certbot --nginx -d example.com -d api.example.com and let it install its renewal timer. The upload limit and the long timeouts matter because lesson videos are streamed through PHP; inside the container nginx already allows 1 GB and 600 s.

    Cookies require HTTPS in production

    The image runs with APP_ENV=production, which marks the session cookie Secure. Logins therefore only work over https://; testing through http://SERVER_IP:3000 will appear to succeed and then drop the session. Always test through the domain.

    Verify the deployment

    Work down this list once; each step covers a different failure mode.

    Check What a pass looks like
    curl -I https://api.example.com/up 200 from Laravel's health route — the API, PHP and the database connection are alive.
    curl -s https://api.example.com/api/v1/settingsData A JSON object with the site settings. If this 404s on the right host, the proxy is sending traffic to the wrong container.
    curl -I https://example.com 200 and content-type: text/html — the Next.js server is up and could reach the API during rendering.
    Open https://example.com Courses and thumbnails load. Broken images mean API_DOMAIN is wrong, or the frontend image was not rebuilt after changing it.
    Open https://api.example.com/admin The Filament login page renders with its stylesheet. Sign in with ADMIN_EMAIL / ADMIN_PASSWORD, then change the password.
    Sign in on the storefront, add a course to the cart No 419, and the session survives a page reload. Both cookies are first-party because the browser calls /api on the storefront origin, which Caddy forwards to Laravel.
    Trigger a password-reset mail The message arrives and its link opens on the API domain. Nothing arriving means MAIL_MAILER is still log or the SMTP values are wrong.

    When changing WEB_DOMAIN or API_DOMAIN later, rebuild the storefront — those values are compiled into the browser bundle:

    docker compose up -d --build web

    The queue worker

    Mail and notifications are queued in the database (QUEUE_CONNECTION=database). The API container already runs a worker for them: supervisord starts php artisan queue:work next to nginx and php-fpm, restarts it if it ever exits, and recycles it hourly so a long-lived process cannot leak memory. There is nothing to install or schedule on the server.

    Confirm it is alive after a deployment, and watch what it processes:

    docker compose exec api supervisorctl status 2>/dev/null || docker compose exec api ps -ef | grep queue
docker compose logs -f api | grep -i queue

    If the queue backed up while the site was down, drain it once without waiting for the hourly cycle:

    docker compose exec api php artisan queue:work --stop-when-empty --tries=3

    Jobs that keep failing land in failed_jobs after three attempts. Inspect and retry them with php artisan queue:failed and php artisan queue:retry all.

    Keep it running

    Backups

    Two things must be backed up: the MySQL database and the storage volume (uploads and lesson videos).

    mkdir -p /opt/lms/backups
cd /opt/lms

# database
docker compose exec -T mysql sh -c 'exec mysqldump -u root -p"$MYSQL_ROOT_PASSWORD" --single-transaction --databases "$MYSQL_DATABASE"' \
  > "backups/db-$(date +%F).sql"

# uploads, videos and the app key
docker run --rm -v lms_lms-storage:/data -v /opt/lms/backups:/backup alpine \
  tar czf "/backup/storage-$(date +%F).tgz" -C /data .

    Schedule both with crontab -e (for example nightly at 03:15) and copy the files off the server — a backup on the same disk is not a backup.

    Updates

    Replace the project files with the new version, keep the existing .env, and rebuild. Migrations run on every boot, so new schema changes are applied automatically and the volumes keep the database, uploads and APP_KEY:

    cd /opt/lms
docker compose up -d --build
docker compose logs --tail=50 api

    If a release ever needs a rollback, restore the database dump and the storage tarball, then start the previous version of the files.

    Routine commands

    docker compose ps                  # status
docker compose logs -f api web     # follow logs
docker compose restart api         # after a config change
docker compose exec api php artisan about
docker compose down                # stop, keep data
docker compose down -v             # stop and DELETE data

    Deployment troubleshooting

    Symptom Cause and fix
    Certificate issuance fails DNS does not point at the server yet, port 80 is blocked, or another server on the host already listens on 80/443. Check dig +short and sudo ss -ltnp | grep -E ':80|:443'.
    Storefront loads but every course, category and login request fails The browser cannot reach https://example.com/api/v1/settingsData: Caddy is not forwarding /api to the API, or the storefront image was built with a different WEB_DOMAIN. Check docker compose logs caddy api.
    Login returns 419, or the cart empties on refresh The host in the address bar is not WEB_DOMAIN — usually www. versus the bare name — so the cookie belongs to the other host. Fix the value, then rebuild: docker compose up -d --build.
    Thumbnails and logo are broken API_DOMAIN changed without rebuilding the frontend, or the value carries a scheme or slash. Use a bare hostname, then rebuild: docker compose up -d --build web.
    Uploading a video returns 413 A proxy of your own sits in front and its body limit is smaller than the file. The bundled Caddy has no limit and the API container allows 1 GB; set the same (client_max_body_size 1024m in nginx).
    Video playback stalls after a minute A proxy of your own times the stream out. Raise it to 600s on the API host block; the bundled Caddy, PHP and nginx already allow it.
    API container restarts in a loop docker compose logs api shows the reason. Usually MySQL is still initialising (the entrypoint waits up to two minutes) or DB_* in .env disagree with the credentials the MySQL volume was created with.
    Mail never arrives, but nothing errors MAIL_MAILER=log, or no queue worker is running. Both are covered above.
    Password-reset or verification links open on http:// APP_URL is not the https:// address of the API — it follows API_DOMAIN, so check that value — or a proxy in front of the stack is not forwarding X-Forwarded-Proto.
    The site works on :3000 but not on the domain A web server of your own is answering the domain instead of Caddy, or Caddy could not bind ports 80/443. docker compose logs caddy and sudo ss -ltnp | grep -E ':80|:443' show which process owns the ports.
