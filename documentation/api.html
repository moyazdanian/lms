    API reference

    The REST layer every screen of the storefront is built on, grouped the way the routes are grouped: public, account, learning, and instructor.

    Nine sections. Useful if you are extending the front end, writing an integration, or debugging why a request from the browser was refused.

    Conventions

    Everything is served from one versioned prefix, returns JSON, and answers with a message on failure.

    Base URL {APP_URL}/api/v1
    Format JSON in and out. Course, lesson, and instructor uploads use multipart/form-data; every other write is JSON.
    Errors 401 when not signed in, 403 when signed in without access to that resource, 422 with field errors on validation, 429 when rate limited, each with a human-readable message.
    Pagination List endpoints that paginate return the standard Laravel paginator shape: data, current_page, last_page, and total.
    Authorization Beyond authentication, model policies for courses, enrollments, orders, and payments decide what a request may touch — so an instructor cannot read another instructor's earnings, and a student cannot read another student's order.

    Rate limits

    Limits are applied where guessing or scraping would be cheap. Exceeding one returns 429 with a message that says to try again later.

    Limiter Applies to Limit
    auth Sign-in, registration, password reset requests, Google redirect, instructor applications. 5 per minute per email and IP address
    reset-password Changing a password while signed in. 1 per minute per email and IP address
    review Submitting a course review. 1 per minute per email and IP address
    video-preview Public course and lesson previews. 30 per minute per IP address, 200 per minute across the site

    Authentication

    The storefront authenticates with a session cookie rather than a token, which is why it can call the API directly from the browser without ever holding a credential.

    1. Ask for the CSRF cookie

      GET {APP_URL}/sanctum/csrf-cookie

      The backend sets an XSRF-TOKEN cookie. Every write request must send it back as an X-XSRF-TOKEN header.

    2. Sign in

      POST {APP_URL}/api/v1/login
Content-Type: application/json
X-XSRF-TOKEN: {token from the cookie}

{ "email": "student@example.com", "password": "…" }

      The response sets the session cookie. From then on, every request from that browser is authenticated as that user, and the cookie expires with the session like any other web session.

    3. Keep the token fresh

      A rotated CSRF token produces 419. The storefront's HTTP client catches that once, re-fetches the CSRF cookie, and retries the request, so a user never sees the error.

    Server-to-server requests

    Protected routes run through Sanctum, which also accepts personal access tokens. No token-issuing endpoint ships in v1 — if you need machine access, issue a token for a user through Sanctum's own tooling and send it as Authorization: Bearer ….

    Webhooks

    Two endpoints exist for gateways to call the site, and they are the reason a payment completes even when the customer never returns to the browser.

    Method Path Notes
    POST /webhooks/stripe Signature verified against the Stripe webhook secret before anything is applied.
    POST /webhooks/mollie The payment is re-fetched from Mollie and verified before the order is finalized.

    Both are exempt from CSRF protection, which is what allows an external service to post to them, and a request that fails signature verification is rejected without touching an order.

    Tests

    The backend ships with a Pest suite covering the parts where a silent mistake costs money: checkout and pricing, the approval workflow, payouts and commissions, media authorization, certificates, and authentication.

    cd localhost

# the whole suite
php artisan test

# one file
php artisan test tests/Feature/PayoutWorkflowTest.php

# by test name
php artisan test --filter=checkout
    Test file Covers
    OrderCheckoutTestCart to order to payment, including zero-total carts.
    FreeEnrollmentTestOne-click enrollment in free courses.
    MarketplaceAccountingTestCommission split and the earnings ledger.
    PayoutWorkflowTestRequest, approve, pay, and reject.
    PayoutPartialAmountTestWithdrawing part of an earning.
    CourseApprovalWorkflowTestSubmit, approve, reject, and edit requests.
    LessonVideoAccessTestWho may stream a lesson video.
    LessonAttachmentTestAttachment upload and authorized download.
    CertificateRevocationRetakeTestIssuing, revoking, and re-earning a certificate.
    LegalPagesTestThe admin-written terms, privacy, and cookie text.
    StorageSettingsTest, S3ConnectionTest, StorageReportTestMedia disks, bucket credentials, and the storage report.
    AuthCookieTest, SocialAuthTestCookie sessions and Google sign-in.

    Tests run against a separate lms_testing MySQL schema with migrations applied automatically, so they never touch your development data. Create it once with CREATE DATABASE lms_testing; before the first run. Run vendor/bin/pint to match the project's code style after making changes.
